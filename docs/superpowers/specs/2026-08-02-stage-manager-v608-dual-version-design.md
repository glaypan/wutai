# Stage Manager v6.0.8 双版本开发设计

## 1. 文档目的

本文定义 `舞台流程表-v6.0.7-安装包` 与 `舞台流程表-v6.0.7beta-design-安装包` 的首批开发方案。两个版本采用“共享内核、双界面”，按协议先行、逐功能同步的方式完成 H1-H4。

本轮目标是增强现场稳定性、Tally、导演审批和移动端操作，不引入新的构建框架，不改变现有离线运行方式。

## 2. 范围

### 2.1 本轮包含

1. H1 WebSocket 断线恢复、增量同步和重复动作防护。
2. H2 Tally 声音、振动、确认、关闭、过期和历史。
3. H3 审批状态机、等待提示、备注、拒绝原因、自动批准和审计。
4. H4 移动端滑动、下拉刷新、长按菜单、横屏双栏和安全区域适配。
5. 补齐 Node.js 原生测试，建立双版本协议与浏览器回归基线。

### 2.2 本轮不包含

1. 多项目和项目模板。
2. OSC/MIDI 输出扩展。
3. SQLite 数据层。
4. 用户系统、REST API、云同步和原生 App。
5. 重构 `public/` 目录或引入前端构建工具。

## 3. 双版本策略

两个安装包继续保持独立可运行，端口、启动脚本和离线资源机制不变。

共享边界：

- `server-standalone.js` 的实时协议、权限校验、事件缓存和日志行为保持一致。
- `stage-core.js` 的事件归一化、状态转换和纯逻辑保持一致。
- WebSocket 消息字段、错误码和兼容规则保持一致。
- 自动测试用例保持一致，必要时仅对界面选择器做版本适配。

差异边界：

- 正式版 `app-source.html` 保持紧凑、稳定和桌面现场操作优先。
- beta-design `app-source.html` 承载新版视觉反馈与移动端布局。
- 两版可以使用不同 DOM 结构，但不能改变共享协议语义。

`public/` 当前不是服务端主页面入口，本轮不在其中复制业务实现。

## 4. 实施顺序

每项功能按以下闭环实施：

1. 定义共享协议和纯逻辑。
2. 修改两个版本的服务端和核心文件。
3. 接入正式版界面。
4. 接入 beta-design 界面。
5. 运行核心、服务端和源码契约测试。
6. 启动两个版本，完成桌面与移动端浏览器回归。

功能顺序固定为 H1、H2、H3、H4。H1 未通过重复 GO 和断线恢复测试前，不开始 H2。

## 5. H1 断线恢复

### 5.1 服务端状态

服务端维护：

- `seq`：进程生命周期内单调递增的事件序号。
- `eventBuffer`：有限长度的可恢复事件环形缓存。
- `processedActionIds`：有限生命周期的动作去重集合。
- `serverInstanceId`：服务进程实例标识，用于识别服务重启。

事件缓存只保存恢复客户端状态所需的结构化事件，不缓存密码、Token 或其他敏感信息。

### 5.2 客户端状态

客户端维护：

- `lastSeq`：最后成功应用的连续事件序号。
- `serverInstanceId`：最后连接的服务实例。
- `connectionState`：`online`、`reconnecting`、`offline` 或 `resyncing`。
- 未提交的本地表单草稿。

高风险控制动作不进入自动重发队列。断线期间只保留未提交输入，恢复后由用户重新确认提交。

### 5.3 连接协议

连接建立后，客户端发送恢复请求，包含 `lastSeq` 和 `serverInstanceId`。

- 实例一致且缓存覆盖缺失区间：服务端返回增量事件。
- 实例变化、序号无效或缓存不覆盖：服务端返回一次完整状态。
- 客户端只按连续序号应用事件；发现缺口时停止应用并请求完整状态。

重连退避为 1、2、4、8 秒，之后保持 8 秒上限，并加入小幅随机抖动，防止大量终端同时重连。

### 5.4 动作幂等

所有可能改变演出状态的客户端动作携带唯一 `actionId`。服务端在权限校验后、执行动作前检查该 ID：

- 首次收到时执行并记录结果。
- 重复收到时不重复执行，返回原动作结果摘要。
- 缺少 `actionId` 的旧客户端仍按旧协议处理，以保持兼容；新版客户端必须发送。

GO、跳转、停止、Cue 触发、Tally 和审批响应均纳入幂等保护。

### 5.5 UI 状态

两版都必须显示在线、正在重连、离线和状态恢复四种状态。重连提示不得覆盖 GO、停止、Tally 或审批等高优先级现场状态。

## 6. H2 Tally 增强

### 6.1 数据模型

每条 Tally 包含：

- `tallyId`
- `senderRole`
- `targetRoles`
- `programIndex`
- `programName`
- `message`
- `status`
- `createdAt`
- `expiresAt`
- 确认和关闭记录

状态使用 `sent`、`acknowledged`、`dismissed` 和 `expired`。

### 6.2 事件

共享事件类型为：

- `tally.sent`
- `tally.acknowledged`
- `tally.dismissed`
- `tally.expired`

全员广播仍使用 `tally.sent`，通过 `targetRoles` 表示全部目标，不额外复制协议语义。

### 6.3 客户端行为

- 声音和振动分别开关，设置保存在浏览器本地。
- 同一 `tallyId` 只产生一次声音和振动，增量恢复不得重复提醒。
- 接收端确认或关闭后，发送端显示处理人和时间。
- 最近历史有固定上限，服务端和客户端均不得无限增长。
- 浏览器不支持振动或音频被策略阻止时，视觉提示仍正常工作并显示非阻断状态。

### 6.4 双界面

正式版使用固定提示条和紧凑历史列表。beta-design 使用更明显的状态面板和移动端底部操作区。两版功能和状态完全一致。

## 7. H3 审批增强

### 7.1 状态机

审批状态只允许以下转换：

- `pending` 到 `approved`
- `pending` 到 `rejected`
- `pending` 到 `expired`

任何终态再次响应都返回冲突错误，不重复执行业务动作。

### 7.2 数据字段

审批请求包含：

- `requestId`
- 请求者和请求角色
- 动作类型与目标节目或 Cue
- 请求原因
- 创建时间和过期时间
- 导演备注或拒绝原因
- 最终操作人和来源

### 7.3 行为规则

- 默认等待提示阈值为 10 秒；请求的实际过期时间由配置决定，不能把等待提示等同于自动拒绝。
- 自动批准仅对配置白名单中的动作类型生效。
- 手动批准、拒绝、自动批准和过期均写入审计日志。
- 拒绝原因原样回传，但在界面渲染时按纯文本处理。
- 审批响应携带 `actionId`，并纳入 H1 幂等保护。

### 7.4 双界面

正式版使用待审批列表、倒计时和紧凑操作按钮。beta-design 使用高可见状态提示和适合触摸的大按钮。两版均要求拒绝原因输入与提交动作明确分离。

## 8. H4 移动端适配

### 8.1 支持行为

- 横向滑动切换节目或字幕。
- 顶部下拉请求最新状态。
- 长按打开当前节目或 Cue 的快捷菜单。
- 横屏使用节目表与控制区双栏。
- 竖屏优先显示当前节目、GO、停止、Tally 和审批状态。
- 使用 CSS 安全区域变量保护顶部和底部操作区。

### 8.2 误触防护

- 手势只从非交互区域开始。
- 输入、按钮、选择器、可编辑内容和滚动条区域不启动切换手势。
- 横向位移、纵向偏差、持续时间和速度同时参与手势判定。
- 下拉刷新仅在主滚动容器位于顶部时启用。
- 手势取消不产生任何控制动作。
- GO 和停止沿用既有现场确认规则，不因移动适配降低保护级别。

### 8.3 响应式要求

覆盖手机竖屏、手机横屏、平板和桌面。固定控制区使用稳定尺寸，动态状态文字不能导致按钮位移或遮挡。桌面键盘和鼠标行为不得回归。

## 9. 错误处理与兼容

- 新客户端能够处理旧服务端缺少增量恢复能力的情况，并回退到全量同步。
- 新服务端接受旧客户端连接，但只对携带 `actionId` 的新版动作提供幂等保证。
- 无权动作继续由服务端拒绝，客户端隐藏按钮不能替代权限校验。
- 所有协议错误使用结构化错误码和可显示消息，不向客户端泄露堆栈、Token 或文件路径。
- 写入 `show.json` 和 `config.json` 前继续执行现有校验，并使用原有安全写入方式。

## 10. 测试设计

### 10.1 核心测试

使用 Node.js 原生 `node:test`，覆盖事件序号、连续性判断、动作去重、Tally 状态和审批状态转换。

### 10.2 服务端契约

覆盖：

- 缓存命中时增量恢复。
- 缓存失效和服务重启时全量恢复。
- 重复 GO、Cue、Tally 和审批响应只执行一次。
- 无权请求被拒绝。
- Tally 终态和审批终态不能非法变更。
- 历史和去重缓存有上限。

### 10.3 源码契约

检查两个版本都包含相同的协议字段、连接状态、Tally 状态和审批状态。检查主运行入口仍为 `app-source.html`，避免误把功能只写入未使用的 `public/`。

### 10.4 浏览器回归

分别启动两个版本并验证：

- 断网后按退避策略恢复，不刷新页面，不重复 GO。
- Tally 声音、振动、确认、关闭和历史。
- 审批批准、拒绝、等待、过期和重复响应。
- 手机竖屏、手机横屏、平板和桌面布局。
- 滑动、长按和下拉可取消，且不会从输入控件误触发。
- 浏览器控制台没有新增错误，关键资源请求成功。

## 11. Git 仓库设计

`E:\AI\git-trae` 可以作为统一 Git 仓库，但 Git 只能跟踪仓库目录内部文件。推荐将两个安装包的可编辑目录和设计文档复制到该目录，原始 ZIP 作为外部备份保留在 `E:\AI\舞台`。

推荐结构：

```text
E:\AI\git-trae\
  stage-manager-v6.0.7\
  stage-manager-v6.0.7beta-design\
  docs\
  .gitignore
  README.md
```

仓库初始化后先提交未修改的 v6.0.7 基线，再开始 H1。不要把运行时目录、日志、临时导出、自动下载的 Node.js 运行时和本地密钥配置提交到仓库。

如果 `config.json` 包含真实 Token、密码哈希或内网地址，初始化仓库前应先决定配置策略：保留不含真实凭据的 `config.example.json`，实际 `config.json` 由本地生成并加入 `.gitignore`。现有数据 `show.json` 是否跟踪应根据其是否包含真实客户和演出信息决定。

## 12. 验收门槛

H1 验收通过条件：短时断网后自动恢复、状态连续、无重复 GO、缓存失效可全量恢复。

H2 验收通过条件：目标角色收到提示、提醒不重复、发送端看到确认、历史有界。

H3 验收通过条件：状态转换唯一、拒绝原因可见、自动批准受配置控制、全部结果可审计。

H4 验收通过条件：四类视口无关键溢出和遮挡，手势可取消，输入控件不误触发，桌面操作不回归。

全部 H1-H4 在正式版和 beta-design 均通过自动测试和浏览器回归后，首批开发才视为完成。
